# Направление 18b: Классификация атомов и цепочки маршрутов

> Дата обсуждения: 2026-10-26
> Связано с: 18_MAP_EDITOR.md (C.5, C.7, C.10, C.12)
> Статус: обсуждение зафиксировано, MVP готов к реализации

## Роль

Документ фиксирует логику классификации пробежек по эталонным атомам
(used / similar / unused), а также концепцию цепочек маршрутов
(chain:) — на случай, если контекстное окно закроется.

## Текущая проблема (на примере 1068-го забега)

### Данные

- Трек 1068: ~7 км, out-and-back
  - Этап 1: дом → пруд (~1.6 км), атом `atom:5 "Дорога до пруда"`
  - Этап 2: круг на пруду (~2.04 км), атом `atom:4 "Круг 1.7"` или похожий
  - Этап 3: пруд → дом (~1.6 км), атом `atom:6 "Дорога от пруда"`
- Эталоны (атомы) в БД: чистые, разделены вручную.

### Симптом

- Бейдж показывает **«Похоже»** (similar), не «Пройдено» (used).
- В карточке атома: `медиана 247 м · 92% · p95 1326 м`.
- Coverage 92% — правильно (круг покрыт).
- Медиана 247 — **неправильно** (артефакт).

### Причина

`computeDeviationFast` (в `coverageIndex.ts`) считает медиану отклонения
**по всем точкам трека**, включая точки разминки/заминки (дом ↔ пруд).

Распределение точек:
- ~600 точек на круге → отклонение 20–40 м
- ~400 точек на дорогах → отклонение 500–1300 м (p95 = 1326 — как раз конец дороги)

Медиана по всем 1000 точкам = 247 м, потому что 40% «плохих»
точек тянут её вверх.

Проверка в `classifyCoverage` для loop:

```js
used =
  coveragePct >= coverageUsed &&   // 92 >= 80 ✓
  repeats >= 1 &&                  // ?
  medianM <= medianMaxM;           // 247 > 100 ✗ — вот тут провал
```

Блокирует **medianM**, не coveragePct.

Дополнительно: `repeats = Math.floor(rawRatio)`, если rawRatio = 0.98
(недо-проход 30 м), то `Math.floor(0.98) = 0`, что даёт `repeats < 1` —
ещё один блокер (второй).

## Решение: два независимых фикса

### Фикс 1. Gated median (для loop)

Считать медиану **только по точкам трека, лежащим в радиусе
`onRefRadiusM` (50 м) от эталона**.

- Для 1068: из 1000 точек остаётся ~600 «на круге», медиана = 20–40 м.
- `medianOk = true` → пройдёт проверку `medianM <= medianMaxM`.
- Для реального зигзага на круге: все 600 точек «на круге», но
  разбросаны в 60+ м → медиана 60+ м → `medianOk = false` (защита работает).

**Код в `computeDeviationFast`:**

```js
// Сейчас devsAll содержит отклонения всех точек трека
// Добавить: gated median только по близким точкам
const gatedDevs = devsAll.filter(d => d <= onRefRadiusM);
const medianM = gatedDevs.length > 0
  ? gatedDevs.sort((a, b) => a - b)[Math.floor(gatedDevs.length / 2)]
  : devsAll[Math.floor(devsAll.length / 2)];
```

### Фикс 2. Integer ratio для linear

Сейчас для linear проверяется `ratio в [0.75, 1.25]`. Не работает
для out-and-back: пробежал атом дважды → `metersOnRef = 3.2 км`,
`ratio = 2.0` → `2.0 > 1.25` → similar.

Заменить на целочисленный ratio:

```js
const integerRatio = Math.round(ratio);           // 2.0 → 2, 1.02 → 1
const isNearInteger = Math.abs(ratio - integerRatio) < 0.2;  // ±20% допуск
const repeatsLinear = isNearInteger && integerRatio >= 1 ? integerRatio : 0;

used = coveragePct >= coverageUsed && repeatsLinear >= 1 && medianOk;
```

- 1 проход → repeats = 1 → used
- Out-and-back → repeats = 2 → used
- Три прохода → repeats = 3 → used
- Половина → repeats = 0 → similar

Аналогично для loop, но через `Math.round`, не `Math.floor`:

```js
if (rawRatio >= 0.95) repeats = Math.max(1, Math.round(rawRatio));
else repeats = Math.floor(rawRatio);
```

### Фикс 3 (опционально). coverageUsed до 75%

Сейчас `coverageUsed = 80%` — строго. Для 1068 coverage 92%, так что
не блокирует. Но для «сложных» маршрутов с небольшими сходами (обход
лавочки, заход на тротуар) — может. Рассмотреть снижение до 72–75%.

## Что было ошибочно предположено (для истории)

В ходе обсуждения были ошибочные интерпретации:

1. **Ошибка 1:** «Дороги — это разминка/заминка».
   На самом деле дороги — **цели**, полноценные маршруты (1.6 км каждая,
   близко к стандартному кругу 1.7 км).

2. **Ошибка 2:** «Пробежка 1068 — это один круг».
   На самом деле это **цепочка** из 3 атомов:
   `[дорога до, круг, дорога от]`.

3. **Ошибка 3:** «Медиана используется только для построения эталона».
   На самом деле медиана используется в **двух разных местах**:
   - `computeMedianTrack` (medianTrack.ts) — для усреднения N пробежек
     в один эталон (то, о чём говорил пользователь)
   - `computeDeviationFast` (coverageIndex.ts) — для вычисления медианы
     отклонений (это то, что ломает 1068)

## Цепочки маршрутов (C.12)

### Концептуальная разница

**`group:` (кластер)** — множество **похожих** атомов.
Пример: «все круги вокруг пруда» = `[atom:4, atom:8, atom:17, atom:23]`.
Порядок не важен. Используется для замены планового атома на другой
из того же кластера.

**`chain:` (цепочка)** — **последовательность** атомов, составляющая
маршрут. Пример: `[atom:5 "дорога до", atom:4 "круг", atom:6 "дорога от"]`.
Используется для описания «как я пробежал в этот раз».

**Ключевое отличие:** кластер — про **типы** (множество вариантов),
цепочка — про **экземпляры** (конкретный маршрут).

### Модель цепочки (гибридный подход)

Цепочка = список **слотов**. Слот описывает «что должно быть»,
не «что конкретно».

```typescript
interface ChainSlot {
  /** Набор кластеров, из которых берутся атомы. */
  clusters?: string[];
  /** Явный список атомов (если не нужна гибкость через кластер). */
  specificAtoms?: number[];
  /** Сколько раз ожидается в слоте (может быть диапазон). */
  expectedRepeats: number | { min: number; max: number };
  /** Можно ли пропустить слот. */
  optional: boolean;
  /** Минимальный coverage атома, чтобы засчитать. */
  minCoverage?: number; // дефолт 90
}

interface Chain {
  id: number;
  name: string;
  slots: ChainSlot[];
  /** Порядок слотов важен? */
  ordered: boolean; // дефолт false
}
```

### Пример для маршрута «пруд с лестницами»

```yaml
chain "пруд-с-лестницами":
  ordered: false
  slots:
    - clusters: ["дороги-до-пруда"]
      expectedRepeats: 1
      optional: false
    - clusters: ["круги-с-лестницами"]
      expectedRepeats: 1
      optional: false
    - clusters: ["дороги-до-пруда"]
      expectedRepeats: 1
      optional: true   # возврат можно не бежать, если другой дорогой
```

### Порядок слотов — свободный

Обсуждение показало: **строгий порядок не работает**.

Пример из реальной практики:
- В субботу побежал **сразу в Лосиный остров**,
- потом (на возврате) **половину стандартного круга**,
- потом **стандартную дорогу домой**.

Порядок: `[Лосиный, круг-в-Лосином, дорога-обратно, половина-круга, дорога-домой]`.
Строгая последовательность «сначала подход, потом круг, потом возврат»
не подходит.

Поэтому `ordered: false` по умолчанию. Сравнение идёт **по множествам**:
«какие слоты покрыты фактом», а не «в каком порядке шли атомы».

Для структурированных тренировок (интервалы, разминка → работа → заминка)
включаем `ordered: true` вручную.

### Гибкость внутри слота

- **Порядок атомов внутри слота не важен:** `[atom:8 + atom:10]` =
  `[atom:10 + atom:8]` = «2 круга из кластера».
- **Один атом может засчитать слот дважды:** `[atom:4 + atom:4]` при
  `expectedRepeats: 2` = ✓.
- **Замена:** `[atom:17]` при `expectedRepeats: 1` и кластер
  `["круги-с-лестницами"]` = ✓ (atom:17 входит в кластер).

### Сравнение план vs факт

План = `chain: X с expectedRepeats`.

Факт = набор атомов с `coverage ≥ minCoverage`, упорядоченный по времени.

Сравнение — **set match** с учётом `expectedRepeats`:

| Слот | План | Факт | Статус |
|---|---|---|---|
| круги-с-лестницами | 1 | atom:10 (coverage 100%) | ✓ |
| дороги-до-пруда | 1 | atom:5 (coverage 100%) | ✓ |
| возврат | 1 (optional) | пропущен | ○ (optional skipped) |

Итог: 2 ✓, 1 ○. План выполнен.

Для варианта «план 1 круг, факт 2 круга»:
- Слот 1: план 1, факт 2 → ⚠ перевыполнено +1.9 км

Для «план круг 1.7, факт круг 2.04»:
- Слот 1: план atom:4, факт atom:17 (оба в кластере) → ⚠ заменено
  (отклонение +0.34 км)

## Открытые вопросы

1. **Унификация карточки атома.** Сейчас в карточке показывается
   медиана из **старой** `computeDeviation` (в `RouteMapEditor.tsx`),
   а классификация идёт по **новой** `computeDeviationFast`
   (в `coverageIndex.ts`). Это два разных алгоритма — карточка и
   бейдж группы показывают разные числа. Унифицировать через:
   - Убрать `computeDeviation` из `RouteMapEditor.tsx`
   - Все данные брать из `refDeviations` (которые уже есть в
     `RouteMapEditor.tsx` и считаются через `computeDeviationFast`)

2. **Настраиваемое количество КП (C.10).** Сейчас 4 КП захардкожены
   в `computeDeviationFast`. Для сложных маршрутов (восьмёрка, петля
   в парке) этого мало. Добавить `checkpointCount` в `CoverageThresholds`,
   слайдер 3–12 в панели «Пороги».

3. **Отображение КП на карте.** При выборе атома — показывать КП
   красными точками. Помогает понять, где КП стоят и почему маршрут
   не засчитывается.

4. **Фильтр «только primary».** В фильтре по атому добавить чекбокс
   «Только primary». Тогда в фильтре «Дорога до пруда» пробежка 1068
   не появится (primary = круг). Это 30 строк в `RouteMapEditor.tsx`.

5. **Direction-aware сравнение для linear.** Live-mode, при котором
   шаги в пробежке и эталоне идут в одном направлении. Если направление
   не совпадает — это другой атом. Это часть C.12 (sequence alignment).

## Что НЕ делаем сейчас

- Явные цепочки (`chain:`) — пока накапливаем примеры
- Sequence alignment — пока set match достаточно
- Унификация карточки — отдельной задачей
- C.10 (настраиваемые КП) — отдельной задачей
- C.11 (векторные карты) — отдельной задачей

## Принятые решения по архитектуре

1. **Кластеры (`group:`)** остаются как есть: множество похожих атомов,
   для замены плана.
2. **Цепочки (`chain:`)** — новая сущность, не путать с кластером.
3. **Слоты в цепочке** — описывают «что должно быть», не «что конкретно».
4. **`ordered: false` по умолчанию** — порядок слотов свободный.
5. **`ordered: true` вручную** — для структурированных тренировок.
6. **Физическая связность соблюдается всегда** — дорога до X не может
   идти после дороги от X (в unordered-режиме это проверяется по
   расстоянию между концом атома A и началом атома B).
7. **Set match** для сравнения план-факт, не sequence alignment.

## Контрольный пример: 1068

**До фиксов:**
- Дорога до: `ratio = 2.0 > 1.25` → similar
- Круг: `medianM = 247 > 100` → similar
- Дорога от: `ratio = 2.0 > 1.25` → similar

**После фиксов (gated median + integer ratio):**
- Дорога до: `repeats = 2, coverage 100%` → **used**
- Круг: `medianM = 30, coverage 92%` → **used**
- Дорога от: `repeats = 2, coverage 100%` → **used**

Все три атома становятся used. Primary = круг (самый длинный).

**С цепочками (Шаг 2+):**
- В карточке 1068: «Покрыто: дорога до → круг → дорога от.
  Primary: круг 2.04.»
- В фильтре «Круг» — есть (used).
- В фильтре «Дорога до» — есть (used).
- В фильтре «Дорога до, только primary» — **нет** (primary = круг).

### Известные ограничения

**1053 (круг без детура) → 98% для атома «Круг с детуром»**

Другие известные случаи, которые ждут C.12:
- Круг с детуром vs круг без детура — не различаются по `coveragePct`
- Круг с лестницами vs круг без лестниц — не различаются (та же причина)
- Цепочки `[дорога, круг, дорога]` — сейчас 3 атома в alsoUsed, primary = самый длинный. Правильная модель — `chain:` со слотами.

## Связь с игровым режимом «Территория» (C.7)

Полигоны в «Территории» — это **треугольники из 3 КП**, захваченных на пробежке. По сути — это тоже цепочки атомов, но не по времени, а по пространству:

- «3 контрольные точки рядом» = группа атомов, связанных геометрически
- «Пройдено через полигон» = трек покрыл все 3 атома-КП
- «Уровень полигона = минимум из уровней КП» = зависит от того, как **часто** захватывались (то есть сколько раз трек покрыл атомы из этой группы)

Поэтому **C.12 (цепочки и слоты) — это фундамент для C.7**. Без цепочек «Территория» будет работать на уровне отдельных атомов, что неправильно: полигон — это композиция нескольких КП.

**Порядок работ:**
1. **C.12** — цепочки, слоты, direction-aware coverage (3–4 часа)
2. **C.7** — игровой режим, полигоны, деградация (5–6 часов)
3. **C.13** — план-факт с гибким сравнением (опционально, 3–4 часа)

### Алгоритм `evaluateChain`

Вход: `chain`, `trackLatlng`, `refTracks`, `thresholds`.
Для каждого слота:
1. Собрать атомы из `specificAtoms` + кластеров `clusters` (по тегам `group:*`).
2. Прогнать `computeDeviationFast` для каждого.
3. Отфильтровать по `coveragePct >= minCoverage`.
4. `aggregate='best'` → выбрать один с max(score); `'sum'` → суммировать `repeats`.
5. Сравнить с `[expectedRepeatsMin, expectedRepeatsMax]` → статус слота.
Общий статус: `complete` / `partial` / `failed` (по наличию failed/partial).

### Фикс `coverageIndex` для linear

Было: `repeats = floor(ratio)` + fallback для `coverage >= 90`.
Проблема: out-and-back просеки (7054 м) при GPS-дрейфе обратного пути
даёт `metersOnRef ≈ 10748`, `ratio ≈ 1.5` → `floor = 1` (или 0 при 1.5).
Стало: CPs-first (как для loop). `checkpointPasses = 2` (туда-обратно)
перебивает `ratio`. Fallback на ratio только если КП промахнулись.
